## 2. 참고와 금지

- 장르 수준의 감각(고딕 성채, 촛불과 달빛, 석재·철·천)만 참고한다.

- 기존 THE HOLLOW KEEP 타이틀 키아트(`games/the-hollow-keep/assets/title-*-hd-v2.webp`)는 **같은 인물의 외형 기준**으로 쓴다. 키아트 자체를 잘라 줄여 스프라이트로 만들지는 않는다(자세·각도가 맞지 않음). 스프라이트용으로 새로 생성한 자세 그림을 밑그림으로 쓰는 것은 §5 경로 A로 허용한다.
- 공용 자산(`assets/`)과 다른 게임(ABYSSFALL)의 그림은 수정하지 않는다. THE HOLLOW KEEP 픽셀 자산은 `games/the-hollow-keep/next/assets/pixel/`에만 둔다.

## 3. 그림체 기준

**빛과 색**
- 바탕은 차가운 청보라·회청색 어둠이다. 빛은 촛불(따뜻한 주황)과 달빛(창백한 청백) 두 가지만 쓴다.
- 빛은 기본적으로 왼쪽 위에서 들어온다. 횃불 근처만 예외로 한다.
- 재질마다 명암 단계는 3~5단계로 둔다. 그라데이션 디더링은 쓰지 않는다. 재질 표현용 디더링(돌결, 녹)만 허용한다.
- "베개 음영"(윤곽 따라 고르게 어두워지는 음영)을 피한다.

**윤곽**
- 1px 선택적 윤곽(sel-out)을 쓴다. 바깥 윤곽은 가장 어두운 색, 빛을 받는 쪽은 한 단계 밝은 색으로 그린다.
- 투명 배경과 맞닿는 가장자리에 중간 투명(안티에일리어싱)을 쓰지 않는다.

**실루엣과 가독성**
- 그림 1픽셀 = 실제 크기에서 실루엣만으로 Ethan과 Noah가 구분되어야 한다.
- 배경은 주인공·적보다 한 단계 어둡고 채도가 낮다. 플레이 판정이 있는 발판은 배경보다 밝고 윗면이 분명하다.

**주인공 외형 (타이틀 키아트 기준)**

| | Ethan · 빛 | Noah · 그림자 |
|---|---|---|
| 실루엣 | 곧고 넓은 어깨, 아래로 길게 퍼지는 롱코트 | 후드와 해진 망토 끝자락, 가늘고 긴 칼 |
| 머리 | 짧은 흑갈색 머리, 후드 없음 | 남색 후드, 그 아래 긴 흑청색 머리 |
| 옷 | 아이보리 롱코트 + 금색 장식, 어두운 가죽 조끼·벨트, 어두운 바지, 장갑·장화 | 남색 망토(보라 안감), 은 장식 검은 가죽 갑옷, 긴 장화 |
| 무기 | 오른팔의 금색 룬 장치, 파란 코어 발광 | 청록색으로 빛나는 가는 장검 |
| 강조색 | 금색 + 파란 발광 | 보라 + 청록 발광 |

**외형 확인 목록 (2026-10-31 추가 — 사용자 "키아트와 차이가 심함")**

검토 때 키아트와 나란히 놓고 확인한다. 자동 검사로는 판단할 수 없다.
- **비율:** 머리 하나가 키의 약 1/6.5~1/7이다(68px 기준 머리 약 10~11px). 키아트처럼 늘씬한 성인 비율을 쓴다.
- **얼굴(옆·3/4):** 코를 앞으로 뾰족하게 튀어나오게 그리지 않는다. 코는 1~2px 음영으로 표현하고, 눈썹·눈은 어두운 1px 획으로 그린다. 3/4 방향 얼굴을 권장한다.
- **자세:** Ethan은 곧은 상체에 넓은 어깨. Noah는 곧고 날렵하게 서며, 목과 머리를 앞으로 숙이지 않는다. 후드 아래로 긴 머리가 보인다.
- **대표 요소:** 실루엣만 보고도 알아볼 수 있어야 한다. Ethan은 코트의 아래로 퍼지는 자락과 금색 룬 팔, Noah는 해진 망토 끝과 가는 장검.

## 4. 기술 규격 (자동 검사 대상)

### 4-1. 격자와 해상도
- 그림 해상도는 게임 좌표 × **scale**이다. scale 1이면 960×540(1단위 = 1픽셀), scale 2이면 1920×1080(1단위 = 2픽셀)이다. 시뮬레이션 수치는 바꾸지 않는다. scale은 `manifest.json`에 적고, 시험 결과에 따라 사용자가 하나로 정한다.
- **타일 크기는 30×30 단위**이다(그림으로는 30×scale px). 화면은 32×18칸이고, 960과 540을 모두 나누어떨어지게 하는 크기다. 2단계의 방은 이 격자로 만든다. 1단계 시험 방의 기존 지형은 격자와 맞지 않으므로, 타일을 잘라 그려도 된다.

### 4-2. 파일
- 모든 픽셀 자산은 **PNG(무손실), RGBA**로 저장한다. WebP·JPEG는 손실 압축으로 픽셀이 뭉개질 수 있어 쓰지 않는다.
- **원래 해상도로 저장한다.** 2배·3배로 키운 이미지를 저장하지 않는다. 확대는 화면에서만 한다.
- 투명도는 **0 또는 255만** 쓴다. 중간값은 쓰지 않는다.
- 모든 불투명 픽셀의 색은 `palette.json`에 있어야 한다. 팔레트는 **최대 64색**이다.

### 4-3. 스프라이트 시트
- 동작 하나를 가로 한 줄 띠로 만든다. 프레임은 왼쪽에서 오른쪽 순서이고, 한 시트의 프레임 크기는 모두 같다.
- 시트 크기는 `frameW × 프레임 수`, `frameH`이다.
- 모든 주인공 그림은 **오른쪽을 보는 방향**으로 그린다. 왼쪽은 렌더러가 좌우를 뒤집어 그린다.
- **기준점(pivot)**은 발 아래 가운데 픽셀이다. 시뮬레이션의 `(player.x + w/2, player.y + h)`가 이 픽셀에 대응한다.
- **발 위치:** 땅을 딛는 동작(`idle`, `run`, `land`)은 모든 프레임에서 불투명 영역의 맨 아래가 `pivot.y - 2` ~ `pivot.y` 사이에 있어야 한다. 발이 뜨거나 땅에 묻히면 안 된다.
- **몸 크기:** `idle` 첫 프레임의 불투명 높이는 시뮬레이션 `height`의 ±15% 안이어야 한다(Ethan 68, Noah 64). 판정 상자와 그림이 어긋나지 않게 하기 위해서다.

### 4-4. 필수 동작과 최소 프레임 수

| 동작 | 이름 | 최소 프레임 | 반복 | 비고 |
|---|---|---|---|---|
| 서 있기 | `idle` | 4 | 반복 | 숨쉬기, 망토·코트 흔들림 |
| 달리기 | `run` | 6 | 반복 | 발이 땅에 닿는 위치가 일정해야 함 |
| 제자리 점프 | `jump-standing` | 3 | 1회 | 상승·정점·하강. 몸을 세우고 무릎을 당긴 자세 |
| 달리며 뛴 점프 | `jump-running` | 3 | 1회 | 상승·정점·하강. **앞으로 기운 도약 자세**. `jump-standing`과 그림이 달라야 함(`jumpKind`, FOUNDATION_SPEC §4-1) |
| 착지 | `land` | 2 | 1회 | 짧게 웅크림 |
| 공격 | `attack` | 4 | 1회 | Ethan: 룬 장치 발사(준비 → 발사 → 반동 → 복귀). Noah: 베기(준비 → 휘두름 → 끝 → 복귀). **첫(준비) 프레임은 2틱 이하** — 게임 판정·탄 발사는 누르는 즉시 생기므로, 준비가 길면 휘두르기 전에 피해가 먼저 보인다(2026-10-31 추가, 자동 검사) |

효과(선택, 있으면 같은 규칙으로 검사): Ethan 룬탄 `fx-rune`(2프레임 이상), Noah 베기 궤적 `fx-slash`(3프레임 이상).

**베기 효과 `fx-slash` 규칙 (2026-10-31 추가 — 사용자 "꺾인 선 같은 이상한 효과")**
- **한 번만 재생:** `loop: false`, 공격 판정 시간 안에 끝난다. **자동 검사:** `loop`가 true가 아님, 이웃 프레임끼리 그림이 다름
- **칼 궤적을 따라 펼쳐짐:** 앞 프레임은 짧은 호, 뒤 프레임은 긴 호 또는 사라지는 꼬리로 진행한다.
- **모양:** 매끄러운 초승달 호. 직선 몇 개를 이은 꺾인 띠로 그리지 않는다.
- **한 획(2026-11-01 추가 — 사용자 "이펙트가 두 줄로 나옴"):** 꼬리·어두운 테두리는 칼날 선에 **붙여** 하나로 이어진 띠로 그린다. 틈을 두고 나란히 그린 평행선은 두 줄로 보인다. **자동 검사:** 프레임마다 6픽셀 이상인 덩어리(8방향 연결)가 정확히 1개(흩어진 작은 점은 제외).
- **채움 없음:** 넓은 면을 단색으로 꽉 채우지 않는다. 밝은 1~2px 칼날 선 + 끝이 가늘어지는 꼬리 + 드문드문 흩어지는 점으로 표현한다. 반투명은 쓸 수 없으므로(§4-2) 점 밀도로 옅음을 표현한다.
- **타이밍·위치:** `attack`에서 칼이 휘둘러지는 프레임에 맞춰 시작한다. 칼을 든 손 위치에서 바라보는 방향 앞쪽으로만 그리고, 몸 뒤로 넘어가지 않는다. 렌더러는 공격 판정 위치가 아니라 `attack` 프레임에 맞춘 위치에서 그린다. **자동 검사(`pixel-render.cjs`, 2026-10-31 추가):** 실제 게임에서 Noah가 좌우로 공격할 때, 효과가 공격 그림 없이 그려지거나, 공격 0번(준비) 프레임에 그려지거나, 몸 중심보다 뒤쪽으로 그려지면 실패.

프레임별 시간은 틱 단위(1틱 = 1/60초)로 `manifest.json`에 적는다. 점프는 시간이 아니라 `vy`로 프레임을 고른다. 예를 들어 `vy`가 크게 음수면 상승, 0 근처면 정점, 양수면 하강이다.

### 4-5. 타일셋
- `tiles.png`는 가로·세로 모두 30의 배수 크기다.
- 필수 타일은 다음 세 가지다. `manifest.json`에 각 칸의 위치를 적는다.
  - `floor-top`: 바닥 윗면
  - `wall-fill`: 벽·바닥 속
  - `ledge`: 얇은 발판. 칸 위쪽부터 16px 높이, 시험 방 발판 두께
- 배경(선택): `bg-*.png`, 960×540, 같은 팔레트를 쓴다.

### 4-6. manifest.json 형식

```json
{
  "version": 1,
  "scale": 1,
  "tileSize": 30,
  "palette": "palette.json",
  "heroes": {
    "ethan": {
      "body": { "w": 42, "h": 68 },
      "animations": {
        "idle": { "file": "ethan-idle.png", "frameW": 96, "frameH": 96, "frames": 4,
                  "pivot": { "x": 48, "y": 95 }, "ticks": [10, 10, 10, 10], "loop": true }
      }
    },
    "noah": { "body": { "w": 39, "h": 64 }, "animations": { } }
  },
  "tiles": { "file": "tiles.png", "cells": { "floor-top": [0, 0], "wall-fill": [1, 0], "ledge": [2, 0] } }
}
```

- `scale`은 1 또는 2이며, 생략하면 1이다. `tileSize`는 30×scale이고, 프레임·기준점·배경 크기는 모두 그림 픽셀 단위로 적는다. 몸 높이와 발판 두께 검사도 scale배로 비교한다.
- `body.w`, `body.h`는 `sim.js` `CONFIG.heroes.*.width/height`와 같아야 한다. 이 값은 게임 단위이며 scale을 곱하지 않는다.
- `ticks`는 프레임 수만큼의 양의 정수 배열이다. 점프는 생략할 수 있다.
- `palette.json` 형식은 `{ "colors": ["#0b0d17", "#1a1f33", ...] }`이다.

### 4-7. 화면 확대 (선명도)
- 캔버스 실제 해상도는 **(960×scale)×k × (540×scale)×k**로 둔다. k는 정수이며, 화면에 표시되는 크기 × 기기 픽셀 비율(DPR) 이상이 되는 가장 작은 값이다.
- 게임은 `setTransform(k, 0, 0, k, 0, 0)`으로 그리고, `imageSmoothingEnabled = false`로 둔다. 이렇게 하면 픽셀이 정수 배로 커져 선명하다.
- 표시 크기가 실제 해상도보다 작으면 브라우저가 부드럽게 줄인다. 그래서 휴대전화처럼 비율이 정수로 떨어지지 않는 화면에서도 픽셀 폭이 들쭉날쭉하지 않다.
- 스프라이트·타일은 **정수 좌표**로 그린다. 시뮬레이션 좌표가 소수이므로 반올림해 그린다(판정은 바꾸지 않음).
- 창 크기·전체 화면이 바뀌면 k를 다시 계산한다.
- `window.HKPlaytest.artStatus()`는 `{ loaded: boolean, failed: string[], scale: 1 | 2 }`를 반환한다(scale은 생략 시 1로 간주).
- 게임은 `setTransform(k×scale)` 기준으로 그린다. 판정 좌표는 그대로 게임 단위다.
- **시험본 전환(삭제됨):** 밀도 시험에 쓰던 `?art=trial-x1|x2`와 `next/assets/pixel-trial/`은 x2 확정 뒤 2026-11-01 사용자 지시로 삭제했다. `build-full-x2.py`가 쓰는 x2 재료는 `next/tools/art-source/density-trial-x2/`에 있다.

## 5. 제작 과정 (이미지 생성 → 실제 픽셀아트)

이미지 생성 도구가 만든 "픽셀아트 느낌" 그림은 대개 픽셀 크기가 섞여 있고 가장자리가 흐려서, 그대로는 이 기준을 통과하지 못한다. 다음 순서를 따른다.

**경로는 둘 중 하나를 고르고 PROVENANCE에 적는다.** 외형을 키아트에 가깝게 하려면 **경로 A를 권장**한다(2026-10-31 수정).

**경로 A — 생성 그림을 밑그림으로 (권장)**
1. 이미지 생성으로 **스프라이트용 자세 그림**을 만든다.
   - 동작·프레임별 한 자세씩, 전신, 오른쪽을 봄
   - 단색 배경, 목표 크기의 정수 배(예: 96px 프레임이면 384 또는 768px)
   - 키아트를 외형 참고로 함께 제시한다.
2. 목표 크기로 줄여 **밑그림**으로 쓴다(최근접 또는 면적 평균). 이 단계의 결과물을 그대로 쓰지 않는다.
3. 배경 제거, 팔레트 양자화, 투명도 0/255 정리를 한다.
4. **손질(필수):**
   - 윤곽 1px 정리, 두 겹 선과 들쭉날쭉한 계단 정리
   - 떠 있는 점과 흐린 가장자리 제거
   - 얼굴과 손 다시 찍기
   - 프레임 간 같은 부위의 위치·색 일치(흔들림 제거)
5. 기준점과 발 위치를 맞추고 시트로 묶는다.

**경로 B — 원래 해상도에 직접 그리기**
- 이미지 생성 그림은 참고만 하고, 픽셀을 직접 찍거나 코드로 그린다.
- 일관성은 높지만 얼굴·옷 같은 세부가 키아트와 멀어지기 쉽다.

**공통**
- 생성 지시문에 특정 게임·작가 이름을 쓰지 않는다.
- PROVENANCE에 경로, 도구, 전체 지시문, 손질 내용, 날짜를 적는다.
- `pixel-assets.cjs`와 `pixel-render.cjs`를 통과해야 한다. 특히 "확대 저장 감지"와 "팔레트 밖 색"은 경로 A에서 손질이 부족하면 실패한다.
